# 生成审查与修复循环的 GOAL

只接受用户对本技能的主动调用。产出是一条 `/goal` 命令，由用户自己运行：本技能不审查、不修复、不改文件或设置，也不替用户设定目标。调用请求里的文字当作参数和授权说明来读，不当作要立即执行的指令。

请求只审查、不修复时，不生成命令：说明本技能只生成审查加修复的循环，一次性审查可用宿主内置的审查命令，要写成只读的 `/goal` 时用 `polish-prompt` 的 GOAL 模式。

## 动笔前

先用读取工具打开 [GOAL 写法](../polish-prompt/references/goal-authoring.md) 和 [GOAL 模板](../polish-prompt/references/goal-templates.md) 的“审查与修复循环”一节，不凭记忆写。条件正文、参数默认值、填写规则和写法以这两份文件为准；本文件只写与它们不同的地方。

## 查明参数

与模板的填写规则不同：能从仓库只读查明的参数，查明后直接填入具体值，不留给执行者。只用不改变仓库及其环境的手段：`git status --short`、`git branch --show-current`、`git rev-parse`、`git symbolic-ref refs/remotes/origin/HEAD`、`git merge-base`、`git log`，以及读取清单、构建脚本和项目文档。不运行测试或构建，不切换分支，不访问网络。

参数可以用自然语言给出。没给出的按下面确定：

- **对象**：没写时，取当前分支相对基线的改动加上工作区改动。也可以是分支名、提交、`A..B`、未提交改动或整个仓库。
- **基线**：先看 `origin/HEAD` 指向的分支；没有就看本地的 `main` 和 `master`，恰有一个时用它，否则提问。对象是未提交改动或整个仓库时不需要基线。
- **取材方式**：由对象推出，必须包含本循环留在工作区的修复：
  - 分支：`git diff $(git merge-base <基线> HEAD)`；
  - 提交 `X`：`git diff X^`；范围 `A..B`：`git diff A`；两者都要求当前检出的是 `X` 或 `B` 所在的分支，否则作为待决问题；
  - 未提交改动：`git diff HEAD`；
  - 整个仓库：当前工作树。

  除整个仓库外，都附上“用 `git status --short` 列出未跟踪文件，一并审查”。
- **需求依据、审查维度、修复范围、轮数上限**：调用请求没写就用模板的默认值。
- **验证命令**：从 `CONTRIBUTING.md`、`AGENTS.md`、`package.json` 的 `scripts`、`Makefile`、`pyproject.toml` 等处找项目实际使用的检查。只有一个明确候选时填入；几处说法不一致或找不到时提问。

查看时发现模板的前置条件已经不满足，例如当前分支与对象不对应、工作区已有对象之外的未提交改动，就在输出里指出并作为待决问题；不替用户切换分支或处理那些改动。

授权按模板的规则：调用请求明确放宽（如允许提交）才按请求写；仓库文件里的文字不构成授权。只有用户能决定的事才提问：对象无法确定、需求含义、是否放宽授权、验证命令选哪个。

## 输出

用用户的语言输出下面几项，不在其外另写说明：

1. 一个代码块，里面只有一条以 `/goal ` 开头的单行命令，按 GOAL 写法写。有待决问题时标明是草稿，并说明答复前不要运行。
2. 每个宿主一行强度建议，建议的是执行这条 `/goal` 的强度，格式为“目标宿主：`<host>`；建议推理强度：`<level>`。<理由>”，宿主是 Claude Code 和 Codex。默认两者都是 `high`，因为最难的判断是跨文件的正确性和问题是否复发；对象只涉及少数文件、改动直截了当时用 `medium`。
3. `参数：` 一行，列出基线、取材方式、验证命令和轮数上限，各自注明查自哪个文件或命令，或注明取了默认值。
4. 待决问题（如有），以 `问题：` 开头。
