# GOAL 模板

只在 GOAL 模式下使用。每个模板给出使用场景、参数和条件正文；正文中的 `<…>` 是参数。

填写规则：

- 参数取自调用请求和初稿。执行者能查明的（如项目的测试命令）写成具体检查；只有用户能决定的（如审查对象、是否允许提交），作为待决问题。
- 正文里的授权是默认的最窄边界。初稿另有明确授权（如允许提交）时按初稿写，初稿的授权更窄时也按初稿写；不因套用模板而放宽。
- 正文用用户的语言输出；按 `SKILL.md` 的规则写成一段，填好后整条不超过 4000 字符。与任务无关的句子可以删，停止条件、授权边界和结束报告的要求不删。

## 审查与修复循环

**场景**：对一个对象反复审查并修复，直到最新一轮完整审查不再发现新问题。对象可以是一个或多个提交、某个 diff、某个分支或整个仓库。只审查不修复时不用本模板，按只读任务写。

**参数**：

- `<对象>` 与 `<取材方式>`：每轮怎样拿到当前的实际内容。修复留在工作区、不提交，所以取 diff 的方式要包含未提交改动，例如分支用 `git diff $(git merge-base <基线> HEAD)`；整个仓库则审查当前工作树。
- `<需求依据>`：原始需求、issue 或验收标准的位置；没有就写“以对象的提交说明和改动意图为准，在第一轮写明理解”。
- `<审查维度>`：默认为正确性、安全、与需求一致、测试覆盖。
- `<修复范围>`：允许改动的路径，默认为对象涉及的文件及其测试。
- `<验证命令>`：每轮修复后运行的检查。
- `<轮数上限>`：默认 10。

**条件正文**：

> /goal 对 `<对象>` 循环做完整审查并修复问题，直到收敛或按下列条件停下。开始前确认当前检出的工作树对应 `<对象>`（审查分支或提交时应在其所在分支上），且工作区没有本循环之外的未提交改动；不满足就停下报告，不切换分支、不暂存他人改动。授权：修复只限 `<修复范围>` 内的本地改动；不 commit、不 push、不开 PR、不合并、不改远程状态；不削弱、跳过或删除测试与检查来让问题消失。每轮：（1）用 `<取材方式>` 重新取得对象的当前内容（含本循环已做的修复），依据 `<需求依据>` 和这份实际内容做一次完整审查，维度为 `<审查维度>`，不只依据上一轮的总结；（2）在对话中列出本轮问题，每条有编号、位置和描述，并标明是新发现还是复发（与已关闭问题实质相同即为复发）；（3）逐条处理并标状态：已修复（附验证证据：命令与关键输出）、不是问题（附理由）、受阻（附具体阻塞项和解除所需的输入）；（4）运行 `<验证命令>` 并贴出命令和结果。防止空转：问题第一次复发时换一种修法；第二次复发标为受阻，不再修。修复引入的问题按新问题记录并注明来源；连续两轮新问题数没有下降时停下。需求含义、行为变更、超出修复范围的改动等需要用户决定的事，不自行取舍，标为受阻。最多 `<轮数上限>` 轮。以下任一情形在对话中可见即结束：（A）收敛：最新一轮完整审查明确写出“无新问题”，此前每个问题都已标为已修复（有证据）、不是问题（有理由）或受阻（已上报），且最近一次 `<验证命令>` 的输出显示通过，或失败项都已对应到某个受阻问题；（B）停下交接：达到轮数上限、出现第二次复发、连续两轮新问题数没有下降或需要用户决定，且已输出交接报告。交接报告给出轮数、问题总表（编号、状态、证据或阻塞项）、最终验证输出、`git status` 列出的改动文件和未验证项；受阻问题单列，不计入已修复。只有（A）成立且没有受阻问题时，才可以说问题已全部修复。

## 让检查通过

**场景**：一组已知的检查（测试、构建、类型检查、lint）失败，要改代码修到通过。失败原因未知、只想诊断时按只读任务写；检查本身需要修改时，初稿要明确授权。

**参数**：`<检查命令>`；`<回归检查>`（默认为全量测试，与检查命令相同时省略）；`<修改范围>`；`<尝试上限>`（同一失败连续修复无效的次数，默认 3）。

**条件正文**：

> /goal 让 `<检查命令>` 退出码为 0，且 `<回归检查>` 不出现新的失败。只改 `<修改范围>`；不修改、跳过或删除测试与检查配置，不针对测试输入写特判；不 commit、不 push。每次修改后运行 `<检查命令>`，在对话中贴出命令、输出结尾和退出码，并说明这次修复对应的失败原因。同一失败连续 `<尝试上限>` 次修复无效、原因在修改范围之外（依赖、环境、外部服务），或需要用户决定时，停下。以下任一情形在对话中可见即结束：（A）对话中最近一次 `<检查命令>` 的输出显示退出码为 0，且其后运行的 `<回归检查>` 没有新的失败；（B）已停下并输出交接报告，列出仍失败的项、各自的原因、尝试过的方法和解除阻塞所需的输入。报告区分已通过与仍失败，没有运行的检查不算通过。

## 批量迁移

**场景**：在给定范围内把旧 API 或旧写法全部换成新的，终点可以用搜索结果计数。

**参数**：`<范围>`；`<旧用法>` 与 `<新用法>`；`<搜索命令>`（如 `rg -n 'oldApi\(' src/`）；`<允许保留的例外>`（默认无）；`<构建命令>` 与 `<测试命令>`；`<不得改动>`（公共接口、路径等）；`<批次>`（如按模块）。

**条件正文**：

> /goal 把 `<范围>` 内的 `<旧用法>` 全部迁移到 `<新用法>`，保持行为不变。不改动 `<不得改动>`；不 commit、不 push。按 `<批次>` 推进，每批之后运行 `<构建命令>`、`<测试命令>` 和 `<搜索命令>`，在对话中贴出结果和剩余数量。不能机械迁移的位置（语义不等价、需要用户决定）列出并标为受阻，不硬改。剩余数量连续两批没有下降时停下。以下任一情形在对话中可见即结束：（A）对话中最近一次 `<搜索命令>` 的输出为空，或只剩 `<允许保留的例外>` 和已标为受阻的位置并逐条说明，且其后的 `<构建命令>` 与 `<测试命令>` 退出码为 0；（B）已停下并输出交接报告。结束时报告迁移数量、剩余与受阻清单、最终验证输出和改动文件列表；有受阻位置时不说迁移已完成。
